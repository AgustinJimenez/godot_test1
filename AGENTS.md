# AGENTS.md

This file provides guidance to coding agents working in this repository.

## Project

First-person survival horror game (Resident Evil-style scarcity) in **Godot 4.6** (Forward+, Jolt physics), written in **GDScript**. This is a learning sandbox: when building systems, briefly explain the Godot concepts involved rather than delivering code silently.

**`docs/PLANNING.md` is the design source of truth.** It holds the milestone roadmap (work in M-order), the Decisions Log (append a row when a design call is made), and open questions with the milestone where each gets decided. Check off roadmap items as they land.

## Commands

The `godot` binary is on PATH (Godot 4.6 mono build).

```sh
python3 -m venv .venv                          # create the ignored development environment
.venv/bin/pip install -r requirements-dev.txt # install pinned lint + hook tooling
scripts/check.sh                    # canonical lint, import, and GDScript parse check
.venv/bin/pre-commit install        # install the repository's local commit hook
godot --headless --import          # reimport assets + register class_name scripts; run after adding files outside the editor
godot --headless --quit-after 10   # boot the main scene for N frames; smoke test for runtime errors
godot --path . res://levels/<scene>.tscn   # run a specific scene
godot --doctool <path> --headless  # dump the FULL engine API reference (all ~900 classes) as XML into <path>/doc/classes
```

`scripts/check.sh` is the single project-wide static validation entrypoint. It
runs the pinned `gdlint` configuration, imports resources, and parses every
GDScript file with Godot 4.6.2. The local pre-commit hook and GitHub Actions
workflow both call this same script. Keep `.gdlintrc`'s 1000-line ceiling and
disabled `class-definitions-order` rule unless a deliberate refactor or project
convention change justifies updating them.

Prefer `--doctool` over web search for any Godot API question: it's generated straight from the exact installed 4.6.2 binary, so it can't drift from a web page describing a different version, and it works offline. Verified against `SkeletonModifier3D`'s new (Jan 2026) IK framework - `doc/classes/FABRIK3D.xml`, `IKModifier3D.xml`, `RetargetModifier3D.xml` etc. all exist with complete, accurate method/property signatures and inheritance chains. Note: this specific binary distribution's dump has **empty prose `<description>` blocks across the board** (confirmed on long-established classes too, e.g. `SurfaceTool` - not just brand-new features), so treat `--doctool` as authoritative for method/property/inheritance structure, not for explanatory text; fall back to web search only for prose explanations of *why*, not *what exists*.

There are no unit tests; verification is done by exercising scenes. Persistent manual acceptance harnesses live under `tests/manual/<domain>/`; temporary one-off capture scenes may use `tests/manual/_<name>_demo.tscn`, but must be deleted before committing. A capture script can drive the player via `Input.action_press()` and direct rotation, then record it with Movie Maker mode:

```sh
godot --path . --write-movie /tmp/out/frame.png --fixed-fps 24 --resolution 1280x720 res://tests/manual/_demo.tscn --quit-after 180
ffmpeg -y -framerate 24 -i /tmp/out/frame%08d.png -c:v libx264 -pix_fmt yuv420p out.mp4
```

Demo scripts that must keep running while the tree is paused (e.g. while an overlay is open) need `process_mode = 3` (ALWAYS) on their root.

Headless import of the FBX packs prints `Can't open file ... Clients/JohnGalt/...` errors — these are broken absolute texture paths baked into the MotusMan FBXs; ignore them (fix at runtime is a material override with `assets/models/pistol_starter/MotusMan/sourceimages/MCG_diff.jpg`).

When visually reviewing animation poses with a throwaway demo scene, aim the camera at the character's front (not side/rear — hides arm motion) and let each clip actually play for ~2s+ before capturing a frame; sampling too early only shows the transition-in and makes unrelated clips look identically "frozen".

Godot 4.6.2 segfaults (`AnimationPlayer::_process_playback_data`) if an `AnimationLibrary` already attached to an `AnimationPlayer` is mutated (`add_animation`) while that player is mid-crossfade — reproduces reliably on the 5th distinct addition in one live session, regardless of which clips. Any lazy/on-demand animation baking must call `anim_player.stop()` immediately before adding to a library the player already owns, never while a blend is in flight (see `play_debug_anim` in `player_body.gd`).

Use `tools/character_editor/character_editor.tscn` to calibrate reusable character/object contact poses. Interactive launches begin empty and progressively disclose six stages: Character, Rig, Animation, Attachments, Pose, and Review. Rig distinguishes a missing skeleton, an unskinned skeleton, an incomplete humanoid map, and an animation-ready rig. Core humanoid roles gate Animation; toe and complete four-joint finger chains remain available for mapping so retargeting does not silently restore hands to rest pose. For static neutral T/A-pose humanoids, Generate Humanoid Rig builds a first-pass Godot-native `Skeleton3D`, `Skin`, anatomically weighted `ArrayMesh`, and reusable scene under `assets/models/generated_characters/`; visually inspect its deformation, and reserve external DCC weighting for complex topology or cleanup. **Never evaluate an autogenerated rig from the isolated 3D model alone:** show the skeleton and the matching-pose rig reference side by side, then compare anatomical landmarks (head, clavicles, spine, hips, elbows, wrists, knees, ankles, fingers, and toes). A ground-level `Root` is a technical motion/origin control, not an anatomical pelvis joint: start anatomical evaluation at `Hips`, render the root as a distinct ground control, and do not draw `Root -> Hips` as a body segment. Imported rigs legitimately differ in whether they have this extra technical root, so its position alone is not evidence of a bad rig. The reference panel defaults to the T-pose page and paginates to the A-pose page; use the page matching the imported mesh's neutral pose, since pose-angle differences are not rig-placement errors. Generated rigs expose colored XYZ rest-position sliders for the selected visible joint; edits preserve the other joints' global positions, refresh inverse skin bind poses immediately, and `Save Rig` regenerates the bundled scene from the source mesh plus persisted joint overrides. The Character selector is a persistent catalog: Import creates an entry, its adjacent menu renames it, `Reset Generated Rig` removes only derived rig/profile files and restores the source, and `Remove from Editor` removes only non-built-in registration; both actions preserve source model files. Imported rig profiles persist beside their model as `<model>.rig.json`. Select or import a character first; the tool displays its static imported/base pose with no attachment and remains on Character while highlighting Rig as the next available step. Entering a step unlocks the following step; later steps remain disabled, while previously reached steps stay available. Selecting the `Select character...` placeholder again fully unloads the current rig and returns to the empty Character stage; it is not merely a prompt item. CLI/MCP calls containing automation arguments still auto-load Player unless `character=` chooses another adapter. The editor can play every animation exposed by `PlayerBody.get_animation_groups()`, load any imported 3D `PackedScene`, attach it to any skeleton bone, tune uniform object scale/position/rotation, and save or open independent JSON presets. It applies additive post-animation rotations across the full MotusMan skeleton, preserving one skeleton and animation state across first- and third-person cameras. Its responsive, scrollable joint matrix includes every skeleton bone, including fourth finger leaf joints, in a collapsible Body → arm/leg → hand/foot → individual finger hierarchy. Collapsing a parent hides its descendants without discarding their expansion state; section headers only disclose rows and must never select a representative bone or alter camera focus. Selecting a 3D joint expands its ancestor sections and reveals its row. The upper-right bone icon toggles the skeleton overlay in every populated workflow stage and preserves its state while switching stages or loaded characters; newly built debug roots must inherit the toggle's current value. It renders thick cyan bone links and selectable joint spheres using the final animated pose. Double-click a visible body region or 3D joint sphere, or single-click the corresponding menu row, to select the nearest bone segment, highlight its row, expand and scroll to its hierarchy section, lock the camera target to that animated joint, and display its XYZ rings (row selection enables the overlay automatically); the colored X/Y/Z toggles independently hide rings and remove them from mouse picking. A single-click drag over the character remains available to Orbit or Move the camera. Sliders edit their bound joint without changing selection or recentering the camera. Drag the selected joint's red/green/blue rings to rotate around the animated local X/Y/Z axes; gizmo edits update the same sliders and exported modifier values. The upper-right viewport toolbar switches empty-space dragging between Orbit and Move, provides zoom-out/zoom-in buttons, and has a frame icon that clears joint focus and restores the default full-body camera. Full-body framing merges every mesh part's transformed AABB, targets its center, and derives camera distance from both character dimensions and the viewport width left uncovered by the panel; never restore MotusMan-specific fixed heights/distances. Selecting an animation reveals a lower-right transport with synchronized play/pause, 1/60-second timeline scrubbing, and current/total timecode; this transport is the sole animation pause control. Dragging pauses both target and raw comparison previews, seeks both, and resumes only if playback was active before the drag. While joint focus is locked, Orbit rotates around that joint; Move releases joint focus and pans the inspection target. Changing the view preset clears joint focus. Enable `Free camera` for captured mouse-look plus WASD/vertical movement. The view menu also provides close-up and isolated-attachment framing. Pause only when tuning a specific animation frame.

Do not start PlayerBody's gameplay idle and then stop, seek, pause, or deactivate its `AnimationPlayer` from Character Editor's parent `_ready()` to obtain a base pose; Godot 4.6.2 can segfault inside `AnimationMixer` during those transitions or on the next `play()`. `PlayerBody.autoplay_default_animation` defaults to true for gameplay, while `PlayerBodyAdapter` sets it false before adding the tool instance to the tree. Preserve that construction order.

Character Editor's preset `Open` button opens a searchable visual grid of saved pose presets instead of immediately showing a raw file picker. Each card identifies its object and uses an object-only thumbnail rendered offscreen when the preset is saved; never use the character viewport as the thumbnail because the body obscures small held props. On first gallery open, missing thumbnails are generated sequentially into `user://character_editor_pose_previews/`; built-in presets may ship cached previews under `assets/ui/pose_previews/`. An optional `thumbnail_rotation_degrees` pose field normalizes presentation of models with inconsistent authored forward axes without changing their gameplay attachment transform, and pose saves preserve it. Selecting a card updates one live `SubViewport` 3D preview beside the inexpensive cached grid; left-drag rotates the model, wheel/trackpad magnification zooms, and the preview toolbar provides equivalent left/right/up/down and zoom-out/zoom-in buttons that repeat while held. `Load Selected` applies the complete pose. Do not auto-rotate the preview because it fights deliberate inspection. While the modal is visible, the root Character Editor must consume any GUI input that reaches `_unhandled_input`; otherwise an initial preview-wheel event can also zoom the character camera behind it. Successfully saved or browsed presets are indexed in `user://character_editor_pose_library.json`; `Browse Presets` inside the modal uses the native OS JSON picker when available, with the Godot `FileDialog` as fallback, for unindexed preset files. Raw 3D models still enter through the Object row's `Browse` button.

Outfit fitting needs two topology catalogs with different meanings. Keep position-welded components
for user selection, UV/hard-normal seam synchronization, and isolation; using only that catalog hides
separate decorative layers that happen to touch. Cache raw index-connected islands as an additional
internal-panel catalog. Do not put those islands into the iterative layer graph: the Peasant boots
expose 50 raw islands but only four useful position-welded components, and admitting every island
expanded fitting from 16 to 328 relations and roughly 160 seconds without converging. For a component
already classified as rigid by bone-aware alignment, three or more substantial islands (64+ vertices)
form a layered construction: the largest structural island supplies a locally interpolated automatic
displacement to nearby panels. Sharing deformation rather than final position preserves their authored
spacing and seam continuity. Do not apply this to ordinary cloth or two-wall foot shells; doing so
reintroduced body intersections in the shirt, pants, and feet.

Outfit Fit's `Compare with original` view must be source-backed, not a duplicate of the currently
rebuilt preview mesh. Duplicate the character/outfit hierarchy for matching cosmetics and transforms,
then replace every comparison outfit mesh with the imported `source` mesh captured by
`OutfitFitEditor`; likewise restore the body's captured source mesh. Keep the comparison copy outside
the editor's mesh state so Auto Adjust and Save cannot mutate it. Temporarily hide debug colors and
control points for an authored-material comparison, and restore their exact prior states on exit.

Character Editor's first animation selector is a package selector. It starts at the real `Select animation package...` state with the clip selector hidden; selecting a package reveals that package's clip selector, and returning to the placeholder clears playback and hides it again. Built-in gameplay/reference packs are read-only runtime groups; user packages are persistent `CharacterAnimationPackage` resources under `assets/animations/packages/` and use the adjacent `...` menu for Create, Rename, and Delete. Import is enabled only while a user package is selected. Choosing a package resets playback to its explicit `No animation` entry; never display its first real clip as selected unless that clip is actually playing. Imported sources are copied under `assets/models/imported_animations/<package_id>/`, recorded in the package resource, and lazily retargeted into the current character's in-memory `custom` `AnimationLibrary` when that package is opened. Changing characters clears only those target-specific baked clips; the package/source metadata remains and retargets for the next character. Package deletion removes its `.tres` registration but deliberately preserves copied source assets. The importer still copies only the selected FBX/GLB/glTF file, not external `.bin` or texture dependencies, so prefer self-contained GLB files or import dependencies explicitly.

Generic pose presets use schema version 3. `attachments` is an ordered array of independently editable slots containing `name`, `role`, `object_scene`, `attachment_bone`, `position`, `rotation_degrees`, `scale`, and `visible`; zero or any number of slots are valid. The Attachments stage selects the slot edited by the existing Object, Attach To, transform, close-up, and isolated-view controls, while Add/Remove and Visible manage the collection. Schema-v2 single-object presets still load, and saves mirror the primary (first) slot into the old `object_scene`/transform fields plus the flashlight legacy keys because `PlayerBody` consumes them. Do not represent a two-handed weapon by attaching two copies: attach one prop to its primary hand, then use an off-hand contact/IK constraint for the second hand. A fresh interactive session has no loaded preset path, so its first `Save` opens Save As and cannot overwrite the gameplay flashlight preset accidentally. `New` clears bone and all attachment transforms into an unsaved pose without changing the selected animation or attachment collection. Selecting a hand or finger exposes a reversible whole-hand Open/Close macro whose center is the detailed pose captured at selection time. Arm, head/neck, leg/hip, and spine selection exposes buttons for suitable authored reference animations; these change the base animation and leave additive fine-tuning values intact. `Save` updates the current preset, `Reload` discards unsaved edits, `Open`/`Save As` switch preset files, and `Save Image` writes a clean UI-free PNG under `user://pose_captures/`. Compare mode replaces the former standalone animation viewer: it plays the selected clip simultaneously on MotusMan and its untouched UAL1/UAL2 source, chooses the source pack through `PlayerBody`'s animation metadata, and keeps pause and timeline seeking synchronized. MotusMan-native clips show only the target. For deterministic agent-driven inspection, pass user arguments after `--`; supported options are `pose`, `animation`, `stage=rig`, `attachment_index`, `object`, `attachment`, `object_position=x,y,z`, `object_rotation=x,y,z`, `object_scale`, `view=full|hand|isolated`, `comparison=true|false`, `bone`, `pick=screen_x,screen_y`, `hand_openness=-1..1`, `time`, `angle=front|back|left|right|top|bottom`, `panel_size=width,height`, `panel_collapsed=true|false`, semicolon-separated `bones=Bone:x,y,z;...`, `capture`, `capture_ui=true|false`, and `dump_bones=<name filter>`. Legacy `flashlight_position` and `flashlight_rotation` arguments remain aliases. A successful screen pick prints `CHARACTER_EDITOR_PICKED:<bone>`; the bone dump prints final local/global transforms as `POSE_DUMP` JSON and exits. Example:

```sh
godot --path . res://tools/character_editor/character_editor.tscn -- pose=res://actors/player/flashlight_grip_pose.json view=hand bone=RightHand time=0.5 angle=right capture=/tmp/character-pose.png
```

An MCP server (`tools/character_editor_mcp/`, registered with Claude Code as `character-editor`) wraps this whole interface as agent tools, in two complementary forms. Invocation-based tools (`load_pose`, `set_bone_rotation`, `set_object`, `capture_pose`, `dump_bone_poses`, `describe_pose` - a rule-based posecode summary, no ML - etc.) each spawn a fresh disposable Godot process per call, mirroring the CLI options above one-to-one. A second set of `*_in_editor`/`live_*` tools (`open_scene_in_editor`, `play_scene_in_editor`, `set_live_view`, `select_live_bone`, `set_bone_rotation`'s live counterpart, `capture_live_pose`, etc.) instead drives an *already-running* editor instance over a local TCP bridge (`addons/mcp_bridge/`), so a human watching the editor and the agent see and edit the same live scene - including `save_live_pose`, which has no invocation-based equivalent since a disposable process has nothing to persist. Screenshots (`capture_pose`/`capture_live_pose`) default to hiding the editor's own UI panel; pass `include_ui=true` to see it. New MCP tool registrations need a Claude Code session restart to become callable; `addons/mcp_bridge/commands.gd` (the actual live-bridge command logic) reloads fresh from disk on every call and needs neither that nor an editor restart, but `plugin.gd` and `pose_debugger_plugin.gd` do (the latter only needs the `reload_editor_bridge` tool, not a full restart). Full architecture, the Godot API gotchas hit while building it (`EngineDebugger.register_message_capture` silently strips its message prefix; GDScript lambdas capture local value-type variables by value, not by reference), and the live-reload mechanism are documented in `docs/character_editor_mcp_plan.md`.

UAL2 (`assets/models/universal_animation_library_2/UAL2_Standard.glb`) is CC0 and uses the same Unreal mannequin bone names and complete finger chains as UAL1, so it reuses `BONE_MAP`. Its debug clips are a separate Character Editor animation group and are retargeted lazily; `A_TPose` is deliberately omitted from the UAL2 group because the shared target library already uses that name for UAL1. `Idle_Lantern` and `Walk_Carry` are the first clips to inspect for right-hand flashlight contact before authoring procedural finger corrections.

Before adding procedural finger rotations for a held prop, compare the final finger transforms against a known grip reference and fit the prop scale/position inside the existing hand cavity first. On MotusMan, UAL2 `Idle_Shield` and `Idle_Lantern` produce identical local finger rotations on both hands; the apparent shield grip comes from the unchanged neutral curled hand pose and its viewing angle. The flashlight at scale `0.12` was wider than MotusMan's grip cavity and could not be fixed by translation alone; `0.08` clears the palm, and a small `RightHandThumb1` Z correction supplies visible opposition. Validate contact from front, side, top, and underneath because a front view can hide palm penetration.

When retargeting animation between differently-authored skeletons, **never transfer raw local rotation deltas or world-space swing rotations directly between rigs**. A bone pose is only meaningful relative to that rig's parent rest frame; skipping that conversion caused the UAL arm spread, wrist freeze, twisted knees, shallow crouch/sitting, and floating collapse poses. Use Godot 4.6 `RetargetModifier3D`'s model-space local-pose formula: `target_parent_global_rest^-1 * source_parent_global_rest * source_pose * source_rest^-1 * source_parent_global_rest^-1 * target_parent_global_rest * target_rest`. The synchronous bake implementation is `_humanoid_retarget_local_pose()` in `player_body.gd`; pelvis position deltas also use the parent-rest conversion plus the target/source hip-height ratio. Use Character Editor's Compare mode for manual confirmation: its grouped selectors use the same animation groups as the in-game debug menu and play the chosen clip on retargeted MotusMan and the untouched UAL source for free-camera comparison from multiple angles. Gameplay aliases resolve back to their source UAL clip through `PlayerBody.get_animation_source_clip()`; MotusMan-native references have no UAL equivalent and display only the target model. The full failed-approach history is in `docs/task_history/ual_animation_retargeting.md`.

Retargeted animations preserve the source clip's `loop_mode`; do not force every imported clip to loop. Only aliases listed in `UAL_LOOPING_GAMEPLAY_CLIPS` explicitly override the source with `LOOP_LINEAR`; jump start/landing and other one-shots must remain `LOOP_NONE`. Character Editor's Compare mode switches with zero blend time so short one-shot poses start in sync; the in-game debug menu keeps its normal 0.2-second crossfade.

Retarget the complete deforming chain, including fingers. An unmapped child bone silently falls back to the target skeleton's rest pose; this originally made every UAL hand look curled even though the source clips contained finger tracks. `BONE_MAP` maps the five finger chains on both hands joint-for-joint. Do not infer visual hand correctness from matching bone deltas or joint-bend angles: an attempted palm-space correction made `Pistol_Shoot` bend metrics match within 0.001 degrees but produced no visible improvement in the user's live test. Different bind geometry, skin weights, proportions, and missing hand/prop contact constraints can dominate the rendered silhouette. For grip/contact failures, inspect those inputs and use an explicit contact/IK solution; do not keep adding rotation corrections merely because numeric skeleton diagnostics improve.

When visually comparing two different character assets, normalize their anatomical rest-facing directions in the comparison harness before judging animation yaw. UAL and MotusMan face about 7.4 degrees apart at rest even with identity node transforms; `raw_animation_comparison.gd` derives the offset from hips/head/shoulder rest positions and rotates only the raw reference. Do not compensate for a comparison-scene asset offset inside gameplay animation tracks.

Apply recurring procedural bone corrections in a `SkeletonModifier3D`, not from an ordinary Node's `_process()`. Direct `Skeleton3D.set_bone_*_pose()` calls persist and can feed the corrected pose back into later animation frames; modifiers are evaluated after animation and automatically restore the base pose after the skeleton update. `PlayerLookPoseModifier` owns the camera-driven torso/neck/head adjustment and caches its visual pose for camera placement. When correcting several bones in one ancestor chain, also snapshot every bone's animation pose before modifying the first parent if configured weights are meant to be absolute; otherwise each child inherits the parent correction and adds its own.

A paused `AnimationPlayer` may not request another skeleton update when a runtime tuning UI changes only modifier data. After editing a paused preview's bone values, call `Skeleton3D.advance(0.0)` so the `SkeletonModifier3D` stack is evaluated immediately; without this, sliders can change stored values while the rendered hand appears frozen.

Gameplay one-shot animations use `PlayerBody.play_action_animation()` and retain priority over locomotion until `AnimationPlayer.animation_finished`; otherwise the per-physics locomotion selector replaces the action on its next tick. Airborne states deliberately interrupt actions. Keep looping states out of this API. Interactable owners declare their body action through `Interactable.animation_name` (`unarmed_interact` by default, `unarmed_pickup` for item pickups), so the player remains independent of door/pickup/note concrete types.

Combat effects must occur at an explicit animation contact point, not when input starts the clip. `PlayerBody.play_action_animation()` accepts a normalized contact ratio and emits `action_contact` at most once if the action reaches that point; interruption before contact cancels the effect naturally. The player stores only the pending attack data and asks `MeleeWeapon` to query at contact, so range and aim are evaluated against the current world state rather than the input-time state. Keep health arithmetic in `Health`, hit discovery in the weapon/component, and animation timing in the body; do not put damage calls inside animation code.

An enemy melee attack commits to its facing once wind-up starts. Turn toward the target before entering the attack, require a small facing tolerance, then lock yaw through contact and visual recovery; continuously steering a strike toward a strafing target produces an unnatural swivel and removes the player's ability to evade laterally. `HumanoidActor` plays UAL2 `Zombie_Scratch` as a retargeted one-shot and compares `AnimationPlayer.current_animation_position` with the exported normalized `attack_contact_ratio` (0.48 by default). Damage is attempted exactly once at that frame and range is re-evaluated then; do not use a fixed seconds-based windup, which drifts when clip length or playback speed changes.

Action recovery windows that are defined as happening *after* an animation must start from `PlayerBody.action_finished`, not when input first starts the clip. Starting a short cooldown at input time lets it expire underneath the animation and provides no real recovery delay. Punches use the exported `punch_delay_min`/`punch_delay_max` range and reject new action requests while the current one-shot owns the body.

Any action that temporarily owns character velocity must explicitly hand it back at its state boundary. The roll snaps horizontal velocity to the current directional input (or zero) when `_roll_time_left` reaches zero; relying on ordinary acceleration to decay the roll's final speed makes the post-roll idle pose slide across the floor.

Held prop visuals use `BoneAttachment3D` on the animated hand, but gameplay aiming lights/rays remain camera-driven. The flashlight GLB is authored about 2 m long on its X axis, so `PlayerBody` scales it to `0.12` and attaches it to `RightHand`. The local looping `unarmed_torch_idle` animation is a retargeted copy of UAL2 `Idle_Lantern`, leaving the imported pack untouched while arm corrections are tuned. The real `SpotLight3D` stays under the camera (offset to the right-hand side); parenting the beam to the animated wrist would make idle/walk sway move the player's illumination and interaction aim independently of the view.

Non-grounded animations may need an equal display-only offset on both models in a comparison scene. The UAL swim clips are authored horizontally around a ground-level origin, so `raw_animation_comparison.gd` lifts both swim previews by 1.35 m while leaving their animation data untouched. Keep presentation corrections in the harness; never bake them into retargeted tracks merely to make a debug floor look right.

## Architecture

Scene composition flows: `playground.tscn` (main scene) = `test_room.tscn` (pure environment, no player) + `player.tscn`; the exterior sandbox follows the same pattern as `nature_playground.tscn` = `nature/nature_environment.tscn` + `player.tscn`. Environment scenes stay player-agnostic; game scenes compose them. The nature environment uses a curated glTF subset of Quaternius's CC0 Stylized Nature MegaKit under `assets/models/stylized_nature_megakit/`; keep its `LICENSE.txt` with the assets. Its three hostile NPCs use Ch10/zombie-girl Mixamo visuals and the same `nav_bake.gd` runtime group-source bake as the test room, with both `Geometry` and `TreeCollisions` registered as sources. `HumanoidActor.character_scene` is visual configuration only: the shared scene still owns collision, navigation, perception, health, and animations, so new compatible humanoid skins do not duplicate body execution. Ch10 uses the numbered `mixamorig5_` prefix; set `character_bone_prefix` accordingly so `HumanoidActor` rewrites the action-pack tracks from `mixamorig_`. Zombie Girl uses the default prefix. Reusable authoring utilities belong under `tools/`; persistent acceptance harnesses belong under `tests/manual/`. `tests/manual/animation/animation_preview.tscn` wraps the test room only to preview the older FBX animation packs, while Character Editor owns UAL comparison and pose editing.

`NPCController` is a body-independent component that stores two switchable dimensions: disposition (`FRIENDLY`, `NEUTRAL`, `SUSPICIOUS`, `HOSTILE`) and behavior (`IDLE`, `PATROL`, `INVESTIGATE`, `CHASE`, `ATTACK`, `SEARCH`, `FLEE`). It places every owner in `npcs` and only hostile owners in `enemies`; events call `set_disposition()`/`set_behavior()`. It deliberately does not execute movement, animation, perception, or attacks. `HumanoidActor` is the current biped executor and assumes a Mixamo-family skeleton, ground navigation, and humanoid clips. A future wolf or flying creature can reuse `NPCController`, `Health`, `Perception`, and damage contracts while supplying its own body execution. Damage makes the current humanoid NPC hostile and starts chase; changing away from hostile cancels a committed attack and returns it to noncombat behavior.

**Object catalogs are authoring data, not player ownership:** `objects/object_definition.gd` describes a reusable 3D asset with a stable ID, category, tags, `PackedScene`, and preview corrections; `objects/object_catalog.gd` collects explicit definitions and provides filtering. Use `tools/object_library/object_library.tscn` to search, filter, and orbit-preview a catalog. The initial catalog is the CC0 KayKit fantasy weapon pack. Do not put inventory counts, use effects, or save-state ownership into these resources: gameplay ownership remains in `Item` + `Inventory`, and selected catalog objects can later be referenced by item/equipment definitions.

**Interaction pattern (used for everything the player touches):** an `Interactable` (plain Node, `components/interactable.gd`) is added as a child *named exactly "Interactable"* of any CollisionObject3D. The player's `RayCast3D` hits the collider, calls `get_node_or_null(^"Interactable")`, shows its `prompt`, optionally plays its `animation_name`, and calls `interact(player)` on E; the owner (door, pickup, note, animation station) connects to its `interacted` signal. New interactables follow this recipe — do not subclass the player or hardcode types.

Interaction key prompts must come from the player's actual ray-selected `Interactable`, because that is the same condition that allows the action. Do not add proximity-only `[E]` world labels: they can advertise an action while the ray is not targeting the collider. The HUD prompt is the single actionable indicator and overlays clear it while gameplay is paused.

**Items are `Resource`s:** `items/item.gd` (`class_name Item`) defines the schema; concrete items are `.tres` files in `items/`. World pickups (`levels/props/item_pickup.tscn`) and inventory slots reference the same resource, so identity comparison (`slot["item"] == item`) is how ownership checks work (e.g. door `required_item`). An item can optionally provide a `world_scene` plus separate pickup and held transforms; the generic pickup instantiates the pickup visual and falls back to its placeholder mesh when absent, so dropping an item recreates the same model without an item-specific pickup scene. Equipping an `Item.Kind.WEAPON` from the inventory instances that scene under a `BoneAttachment3D` on its `held_bone` (`RightHand` by default), giving first- and third-person views the same skeleton-driven visual. Item kind and attachment are metadata/visual state only: actual attack behavior still belongs to a weapon component such as `PistolWeapon`. The inventory (`components/inventory.gd`, Node child of Player) emits `changed`; UI refreshes reactively from that signal only.

**Damage stays component-driven:** damageable actors expose a child named `Health`. `PistolWeapon` applies hitscan damage; `MeleeWeapon` uses a short capsule spanning the camera-to-reach segment on the damageables physics layer, then discovers the collider's `Health`. Equipped items supply `melee_damage` and `melee_range`; `Q` plays the retargeted sword attack for held KayKit weapons and alternates jab/cross with weak fallback damage when unarmed. The query spans the full reach rather than sampling a sphere only at its tip, so very close actors remain hittable. Hostile NPC attacks use the same `Health` contract against the player.

Combat feedback is driven from confirmed applied damage, never speculative input. Pistol hits spawn `DamageHitEffect` at the ray's exact collision position/normal; melee first selects with its forgiving capsule, then ray-refines contact against that selected body and falls back to its upper body only when no direct contact exists. `WorldHealthBar` listens to sibling `Health`/`NPCController` components and is visible only within 7 m while that NPC is attacking or for 3 seconds after damage; it stays hidden when dead and respects world occlusion.

Actor navigation owns world translation. The borrowed Mixamo walk/run clips contain several meters of hip translation per cycle; `HumanoidActor._make_clip_in_place()` removes the accumulated horizontal hip travel from each copied clip before looping it, while preserving vertical bob and cyclic stride offsets. Do not combine translating root animation with `CharacterBody3D` velocity unless implementing an explicit root-motion system, or the rendered mesh will advance independently and snap backward at every loop.

Godot 3D actor forward is local `-Z`, and positive rotation around Y turns `-Z` toward world `-X`. Converting a desired horizontal direction to actor yaw therefore uses `atan2(-direction.x, -direction.z)`; using a positive X argument makes the actor turn exactly away from its target. The current Mixamo zombie FBXs are authored moving/facing along visual `+Z`, confirmed by their unmodified walk/run hip translation, so `HumanoidActor.character_yaw_offset_deg` defaults to 180 degrees on the visual child. Keep AI, perception, collision, and the facing-debug arrow on the parent actor's `-Z`; configure visual forward separately for replacement assets. Shoulder/up cross products identify the facing axis but cannot by themselves distinguish anatomical front from back, so do not use that diagnostic to choose the sign.

While a humanoid enemy is chasing, navigation controls its velocity but the player position controls its facing. Looking only toward `NavigationAgent3D.get_next_path_position()` can make an aggro enemy visibly face a path corner instead of its target. Patrol/investigate/search still face their movement direction; committed attacks retain their separate yaw lock.

`CSGBox3D` auto-generates UVs normalized 0-1 per face regardless of that face's actual size, so driving a tileable pattern off `UV` distorts badly on a non-square face (a 36m x 3.6m wall squashed a diamond pattern into 15x-too-wide horizontal stripes). Fix: compute the pattern coordinate from world-space position (`(MODEL_MATRIX * vec4(VERTEX,1)).xyz` in `vertex()`) instead of `UV`, so a `tile_scale`/`texture_scale` uniform means "meters/tiles per meter" consistently on any box size; keep a `use_world_uv` toggle for curved surfaces like `CSGCylinder3D`; whose circumferential UV already wraps proportionally to real arc length and doesn't need it. See `shaders/damask_wallpaper.gdshader` and `shaders/ceiling_tile_grid.gdshader`.

Sibling top-level `CSGShape3D` nodes (e.g. separate `Floor`/`Ceiling`/`Wall` boxes) are independent solid meshes, not automatically hollowed around each other. Anything placed at a world position inside another solid box's volume is invisible from outside it, occluded by that box's own near face — this is not a transparency/z-fighting bug, the geometry is just embedded in solid matter. Ceiling-mounted fixtures (light panels, the vent) and wall baseboards all hit this in `levels/backrooms_level0.tscn`/`ceiling_vent.tscn`: the fix is either a real CSG subtraction cut as a child of the solid shape (like `DoorCut`/`DoorCutEast` under `WallNorth`/`WallEast`), or — for a shallow surface-mounted look — simply keep the object's near face just outside (below, for a ceiling mount) the solid shape's boundary. A CSG union child (default `operation = 0`) with its own distinct `material` still renders with that material in the combined mesh — used for the baseboard trim, a plain union child of each wall rather than a subtraction.

An `OmniLight3D` embedded inside solid geometry (not just its visual fixture mesh, the actual light node) produces abnormal scene-wide glow/haze rather than simply looking wrong locally — moving a ceiling light's visible panel flush against the ceiling is fine, but the light-emitting node itself must stay in open space below the solid ceiling box, decoupled from the panel's mount position if the panel is flush enough to otherwise pull the light source inside the box too.

`MultiMeshInstance3D` is the right tool for real (non-baked-texture) repeated geometry at scale — `components/ceiling_tile_grid.gd` builds physical ceiling tile panels with real gaps this way (3600 instances for a 36m x 36m room) instead of thousands of individual CSG/Mesh nodes, which would bloat the scene tree and draw calls.

`PlayerFootIKModifier` (`actors/player/player_foot_ik_modifier.gd`) plants each foot on the raycast-detected ground and reorients it to match. Don't align a bone's "down" axis to a target with a single shortest-arc `Quaternion(from, to)` applied to the whole basis — that leaves the twist around the down axis to an implicit, unstable perpendicular-axis choice, which can spin the whole bone 90+ degrees whenever the animated direction ends up close to opposite the target; build the corrected basis from two explicit reference vectors (down + a forward reference) instead, see `_compute_new_foot_basis_world()`. Separately, don't snap a rest-pose "which local axis is down" measurement to the nearest cardinal axis (±X/±Y/±Z) as a simplification — for this rig the nearest axis was still `~26.6 degrees` off true down, and since child bones (toe, toe-tip) get rebuilt through that same quantized frame every frame, the rounding error reproduced itself exactly as a visible kink that looked like a rig/animation problem but wasn't; use the exact rest-pose direction instead. When diagnosing a joint chain, log/display each segment's own **absolute** angle from a world axis, not the bend angle relative to the previous segment — a bend-relative angle can stay pinned at an identical value across totally different poses whenever that segment is rigidly rebuilt from a fixed rest-pose offset, which hides exactly the bug you're trying to see instead of revealing it. Full bug trail (including a third bug — fixing the quantization restored a natural toe-down stance that then clipped through the floor, fixed by predicting per-leg ground clearance from orientation *before* the position solve) in `docs/task_history/foot_ik_debugging.md`.

Applying full ground-plant IK correction unconditionally every frame, with no concept of gait phase, kills a walk cycle's natural foot lift entirely — on flat ground the raycast finds essentially the same ground height under the foot on every frame, so the leg gets bent to plant there even while the animation is trying to lift the foot through the air for a step. Diagnosed exactly by logging a real bone's world position over N frames with the modifier off vs on and comparing (a foot Y range of 27cm with it off collapsed to a perfectly flat 0cm with it on) — see `docs/task_history/foot_ik_debugging.md`'s Bug 4 for the full technique. Fix: blend the IK target (and the corrected orientation, via quaternion slerp) between the raw animated pose and the full correction, weighted by how fast the *animated* foot is currently moving vertically, not by its height/distance from the ground target — height conflates "large one-time correction needed" (e.g. standing still on a tall stair) with "actively swinging," and broke static stair-idle the same way Bug 2 above did. Also: `SkeletonModifier3D._process_modification_with_delta()` is called **twice per physics tick** — once with `delta=0.0`, once with the real delta — so any per-frame "previous value" reference used for a velocity/rate calculation must only be updated on the real-delta call, or every real sample ends up diffed against a same-tick duplicate and reads as zero movement forever.

A follow-up fix for that swing-vs-stance blend (gating on the *sign* of vertical velocity, not just magnitude, to stop a smooth arc's low-speed approach to its peak from reading as a landing) introduced a worse regression: a hard sign cutoff at exactly 0 means any barely-positive velocity — an idle clip's own subtle breathing sway, or plain float noise — zeroes the correction for that one frame and snaps the leg back to the raw animated pose, visible as a sudden twitch on completely static poses, not just during walking. **Don't gate a noisy per-frame signal with a hard cutoff at exactly the boundary value** — a real-world animated signal (even from a "static" idle pose) has enough per-frame noise that it will eventually cross zero and trigger the cutoff; use a continuous scale/penalty instead (here: multiply rising velocity by a penalty factor before comparing to the swing threshold, rather than disqualifying it outright) so small noise stays harmless while the much-larger real signal still gets suppressed. A pure scale/penalty on its own can still be insufficient, though — noise near `threshold / penalty` in magnitude still produced a smaller but user-visible partial dip even after the penalty fix, only caught because the user kept testing after the "fixed" commit rather than assuming done; the actual fix needed both a scale/penalty *and* a small dead zone (`velocity_noise_floor`) below which the signal is ignored outright regardless of sign, verified this time across every idle character in the scene at once, not just the one platform spot-checked the first time. Full trail in `docs/task_history/foot_ik_debugging.md`'s Bug 5.

Foot IK idle step-down planting (`step_down_*` exports on `player_foot_ik_modifier.gd`) makes a stationary foot hovering over a lower surface (stair-riser straddle) ease down and plant instead of floating. Route the destination through wherever real movement input already flows (e.g. substitute for `direction` in `player.gd`'s own movement code) so it rides the exact same path a real walk up/down these stairs already uses and proves correct. See `CURRENT_TASK_IK_FOOT.md` for a still-open bug (one specific drop's `ground_weight` gets permanently stuck at 0 in live play only, never reproduced headlessly) and a newly-found one (the whole-body walk doesn't stop after the one foot that needed it, cascading down an entire staircase from idle).

**Any "must sustain N consecutive frames" counter fed by per-frame animation velocity will flicker on ordinary idle noise if it hard-resets to 0 on a single frame over threshold.** Hit twice in the same investigation (`_step_down_static_streak` in `player_foot_ik_modifier.gd`, `_falling_streak` in `foot_ik_gait_tracker.gd`): idle-animation jitter crosses a ~0.03-0.06 m/s threshold often enough that the streak could barely ever sustain 4 frames, so the classification it gated flickered true/false continuously and a downstream `contact_lost` check kept force-resetting `ground_weight` to 0 before it could finish ramping — the foot read as correctly classified in any single snapshot yet visibly never moved. Fix: decay by 1 on marginal noise (up to ~2x threshold) instead of resetting to 0; keep a real, large reversal resetting immediately, or a genuine swing start reads as still planted and the foot sinks into the tread it's swinging over (confirmed by `FOOT_IK_BODY_PENETRATION_CHECK` after too-lenient a first attempt at this fix). The same principle applies to any watchdog/recovery timer built on top of such a counter — an unconditional reset-to-0 on the counter's own reset path can silently prevent the watchdog from ever accumulating far enough to fire.

**Do not "fix" `SkeletonModifier3D`'s twice-per-tick call by skipping the whole delta-zero call outright — gate individual state updates instead, and never trust a headless-only trace as proof this class of fix is safe.** The established, working mitigation (see the paragraph above) is to gate each *specific* per-frame reference update on `delta > 0.0`, leaving the delta-zero call free to still run everything else (bone solving, pose re-evaluation for the paused-tuning debug panel, etc). A later attempt instead added `if delta <= 0.0 and not get_tree().paused: return` at the very top of `_process_modification_with_delta()`, reasoning that the delta-zero call was corrupting more than just one velocity reference (it was — a walking-specific weight-stuck deadlock). Headless `--fixed-fps 60` trace analysis showed this fully fixed the deadlock with zero regressions across the full `check_foot_ik.sh` suite. Live in the editor it broke Foot IK completely — even idle poses that had worked all session — because the live/interactive call pattern for this modifier does not necessarily match the headless one; whatever assumption "one call is always the real delta, the other is always exactly `delta=0.0`" rested on evidently doesn't hold universally. Reverted immediately once live-reported. **A headless trace or an automated check passing is not sufficient evidence for changes to this specific twice-per-tick behavior — get a live in-editor confirmation before treating it as fixed**, even (especially) when the headless data looks clean.

**Unbounded per-frame debug logging left enabled during ordinary interactive play, not just automated one-shot runs, can silently kill the whole editor debug process.** `foot_ik_preview.gd`'s `STAIR_FOOT_TRACE` JSON trace was only ever meant for the one-shot `--foot-ik-check` capture, but a stray `walker["trace_enabled"]` guard let it re-fire on every iteration of a walker that loops forever during interactive testing. Over a long session this overflowed Godot's own Output console buffer and silently halted the debugger (`ERROR: [output overflow, print less text!]` / `--- Debugging process stopped ---`) — every subsequent live readout was from a dead process and looked exactly like "nothing reacts to any fix," costing a long unproductive debugging detour before a screenshot of the Output panel revealed it. If a "definitely tested live, still broken" report resists several plausible fixes in a row, check the Output panel for this exact message before spending more time on the code — and gate any new per-frame print/logging behind the automated-check flag it was built for, not left unconditional.

**A "trust this state, stop reacting to noise" flag (Foot IK's idle-freeze, `update_idle_freeze()`) must bypass every downstream computation that state is supposed to protect, not just the obvious ones.** Freezing correctly bypassed the raycast re-search and the distance-based `contact_lost` check, but `_raw_weight()`'s own velocity-based formula in `foot_ik_gait_tracker.gd` never checked the `frozen` flag at all — so a genuinely frozen foot (confirmed via the debug JSONL's `freeze_streak` field pinned at its cap, meaning actually frozen, not still accumulating) still had its `ground_weight` nudged down every idle-animation loop by ordinary sway crossing `velocity_noise_floor`, producing a small but real, perfectly periodic pop each cycle — this outlasted two earlier, correct-but-incomplete fixes (widening the animation-discontinuity suppression window, then narrowing it back down) that reduced the severity without eliminating it, because neither touched this actual code path. Fix: once `frozen`, force `raw_weight = 1.0` unconditionally, the same as the existing `force_plant`/`skip_velocity_gate` overrides. When adding a "stop reacting, trust this" flag, grep every function that independently derives the value it's meant to protect and check each one explicitly — a partial bypass measurably reduces a bug's severity, which can look like progress, but leaves it defeated by whichever path wasn't updated.

**Before rate-limiting a shared per-frame value, `grep` every write site — not just the one the bug report points at — and confirm the fix by checking the value a *consumer* actually reads, not the bookkeeping variable you edited.** Fixing Foot IK's turn-snap bug (`_smoothed_target`, tens of cm popping in one frame during a fast rotation/flick-turn) took three rounds because each fix touched only one of three independent writers: `player_foot_ik_modifier.gd`'s ordinary raycast-tracking path, its reach-limit retraction path, and `foot_ik_stair_predictor.gd`'s stair-support latch (`_apply_support_contact()`) — clamping the first two measurably helped but left the third, largest snap completely unchanged. Worse, the clamped bookkeeping variable (`_smoothed_target`) wasn't even what got rendered there: `_apply_support_contact()` set `leg["target"]`/`leg["ground_target"]` (the value `_leg_solver.solve()` actually reads) directly from an unclamped `_support_ground_target`, so the clamp silently did nothing even though it "looked" applied — caught only by adding a temporary debug print at the write site and confirming the clamp's own math executed correctly, then noticing the *rendered* trace still jumped instantly. If a fix compiles, passes checks, and the bug still reproduces byte-for-byte identically (same frame, same magnitude, down to the decimal), suspect the fix touched the wrong variable, not that the fix is subtly wrong. Also: two of the fix attempts here (a blanket clamp, then one gated on the `step_down` gait flag) both regressed `FOOT_IK_BODY_PENETRATION_CHECK` with the *exact same* failure signature (15 samples, 0.308m max depth) — identical regressions across differently-gated attempts meant the gate wasn't distinguishing the two cases at all (`step_down` isn't true for every frame of a real stair descent). The signal that actually worked was independent of gait timing entirely: the support surface's contact-normal tilt (`dot(Vector3.UP)`) — near 1.0 for a flat stair tread (which needs an instant plant, or the pelvis sinks into the riser gap while a rate-limited target lags behind), well below it for a sloped ramp (safe to smooth). When gating a fix between two behaviors, prefer a signal that's a structural property of the situation (surface shape, geometry) over one that's a transient phase flag (gait/animation state) which may not hold on every frame you need it to.

**Animation loop-reset seams are a recurring, cross-cutting gotcha, not a one-off Foot IK bug** — `AnimationPlayer.current_animation_position` resets backward instantly on loop, a real discontinuity that any code diffing across it (velocity) or reading a raw bone pose on that exact frame (a two-bone solve amplifying a tiny seam) can turn into a visible snap or spike. It has already hit four independent Foot IK consumers, each found live and fixed separately. Before debugging a periodic, once-per-animation-loop snap in *any* system (not just feet), read `docs/known_issues/animation_loop_reset_seam.md` first — it documents the detection mechanism already built (`update_animation_discontinuity()`, `_animation_discontinuous`, `_velocity_suppressed`), which consumers already had to respect it and why, a live cross-character instrumentation pitfall that cost real debugging time, and (now resolved, with the full trail kept as a worked example) the periodic walking/sprinting snap that turned out to be two separate bugs stacked on top of each other.

**A periodic snap that looks tied to an animation loop-reset isn't necessarily caused by it — verify the fix actually moves the originally-reported symptom, not just a plausible-looking corrupted-state bug found along the way.** The walking/sprinting snap documented in `docs/known_issues/animation_loop_reset_seam.md` had two independent causes. Bug 1 (real, worth fixing, but not the dominant one): `PlayerFootIKModifier` runs twice per physics tick (a real call, then a phantom `delta=0` call — see the twice-per-tick entry above); both the pelvis-sink logic and the leg solver's own pose read were calling `skel.get_bone_global_pose()` fresh on *every* call, so the phantom call read back the real call's own same-tick write (pelvis is hip's parent) as if it were untouched animation — confirmed by printing the "fresh" value on consecutive calls and finding it exactly matched the previous call's own output. Fixing this (cache the true pre-write baseline once per real tick, share it between the pelvis-sink and leg-solver reads) reduced but did not eliminate the visible snap. Bug 2 (the actual dominant cause): `target_max_speed` — the hard cap on how fast the smoothed ground-contact target may move per frame — defaulted to `1.5` m/s while the character's own `walk_speed` (`player.gd`) is `3.2`, `sprint_speed` `5.8`, `roll_speed` `7.0`. During any sustained walk, the raw ground target legitimately moves at player speed but the smoothed one could only chase at 1.5 m/s, so the gap grew every stride until the pelvis's reach-limit sink maxed out — confirmed by logging the reach-limit computation's own inputs and finding the hip-to-target horizontal distance reaching 1.7–3.3m during *ordinary flat walking*, an impossible distance for a real leg, meaning the "reach limit" logic was reacting to smoothing lag, not genuine overreach. Fixing bug 1 alone left the snap at full, unchanged magnitude — only fixing bug 2 (raising `target_max_speed` above the character's actual top speed) eliminated it. When a live before/after comparison of a "fix" shows the reported symptom unchanged in magnitude, don't conclude the investigation on the strength of a real, confirmed-corrupted piece of state alone — that state can be a second, genuine bug that just isn't the one producing the visible symptom.

**A "more general" reformulation of a formula can be a mathematical no-op if it doesn't account for what the inputs are already guaranteed to satisfy — verify with live-varying inputs, not just "it compiles and the shape looks right."** Investigating a small (~1cm) toe clip on a tilted ramp, the working theory was that `_measure_leg_sole_depth()`'s single flat-pose scalar couldn't bound clearance correctly at other tilt angles, so it was rebuilt into a "direction-aware" version: store the full sole-mesh point cloud in the foot's local frame, then each frame re-project every point onto the *current* ground direction and take the max (`(foot_basis * point).dot(desired_down)`). This looked like a strict generalization of the flat scalar and compiled/ran fine. It was actually mathematically identical to the original at every tilt, not just similar — because `_compute_new_foot_basis_world()` builds `foot_basis` so its own local down-axis *is* `desired_down` by construction (the whole foot rotates to match the ground normal), so `(foot_basis * point).dot(desired_down)` algebraically collapses to `point.y` (the point's plain local-Y value) regardless of tilt — the exact same number the flat scalar already computed. Caught only by adding a debug print of both the input tilt (varying: 1.0, 0.97, 0.87, 0.71 across normals) and the output offset side-by-side, and noticing the output never changed despite the input clearly varying — a fix that's *supposed* to be direction-sensitive but produces a constant should be treated as a red flag on the formula itself, not "must be a separate remaining bug." Before generalizing a computation to depend on more inputs, check whether the object it operates on (here, `foot_basis`) was already built to make that dependency vanish algebraically.

## Conventions

- Static typing everywhere in GDScript; `&"action"` StringNames for input actions; input actions only (never key checks) — the map lives in `project.godot`.
- Composition over inheritance: reusable behaviors are child Nodes (`components/`), not base classes. Signals up, calls down.
- snake_case files/functions, PascalCase nodes/scenes; scene + its script live side by side (`actors/player/`, `levels/props/`).
- `.tscn`/`.tres` files are hand-editable text; when writing them, `load_steps` = total ext+sub resources + 1.
- Commit at milestone boundaries with a summary of what the milestone added.
- **Never commit gameplay/visual/animation changes on the strength of automated verification alone (headless checks, Movie Maker frames, print diagnostics).** These have shipped broken twice in one session despite passing recorded-frame review each time — screenshots and logs can look plausible while the actual interactive behavior is wrong. Implement, verify as best as possible, then stop and wait for the user to manually test in the editor and explicitly confirm it's working before committing.
- **When your own repro attempts don't reproduce a bug the user hits reliably, that mismatch is the signal, not noise.** A "black face" symptom in Character Editor cost two wrong fixes (a lighting theory, then a plausible-but-wrong null-material patch) before asking the user for their exact click sequence found the real cause (`_on_view_selected` nulling a mesh resource) in one shot. All view/mode actions must guard `supports_isolated_attachment`, `body.mesh`, and `_full_body_mesh` before swapping mesh resources; non-comparison characters hide the otherwise meaningless Edit/Compare row and `_on_editor_mode_pressed()` rejects them defensively. Diagnosing from a screenshot invites a plausible-sounding wrong answer; if several of your own repro attempts come back clean while the user's doesn't, stop theorizing and ask for their exact steps instead of trying a third variation blind. Full trail in `docs/task_history/character_editor_import_feature.md` (Bug 9).
- **Verification loop for interaction-sensitive behavior (Foot IK, stair/step movement, animation):** reproduce headlessly first via throwaway `--<case>-verify` branches in the persistent harness (must be deleted before committing), reading ground truth from the modifier's post-solve snapshot (`_final_bone_poses`) rather than `Skeleton3D.get_bone_global_pose()` at idle/deferred time, and printing the decisive numbers so the trade-off is measurable. But **when the `character-editor` MCP tools are available, also close the loop live yourself instead of relying only on the user to reproduce and report back**: `mcp__character-editor__get_editor_state` confirms what's open and whether it's already playing, `play_scene_in_editor()` (F6-equivalent) starts it, `stop_scene_in_editor()` stops it. The Foot IK debug overlay (`foot_ik_debug_overlay.gd`) writes a rolling per-frame JSONL trace (`user://foot_ik_controlled.jsonl`, capped at `CONTROLLED_TRACE_MAX_FRAMES`) the whole time `foot_ik_preview.tscn` is running — play it, `sleep` 15-20s (a plain sleep here is fine and expected, not a wasteful poll), stop it, then read the JSONL directly. This exercises the *actual* live/interactive call pattern (relevant given the twice-per-tick lesson above — a headless `--fixed-fps` run is not proven equivalent) without waiting on the user's own testing loop, and is how the idle-freeze bug above was ultimately caught and confirmed fixed: a periodic weight dip invisible to every headless automated check, verified gone by replaying the same scene and diffing a fresh capture against the prior one. When the design has real alternatives (e.g. how to handle drops beyond the step envelope), write the options into `CURRENT_TASK_IK_FOOT.md`, implement the user's chosen one, and still get final manual confirmation before committing gameplay-affecting changes.
