# 016: ALS Locomotion Port Prototype

## Overview
Explore porting ALSHost's (UE5/ALS-Community) third-person locomotion feel — grounded movement, blended directional animation, rotation modes, basic jump/fall — onto a from-scratch Godot character in a brand-new, isolated scene. Not a rewrite of the existing `actors/player/*` system: that system (player.gd/player_body.gd + the foot IK stack) has two open bugs (`013`, `014`) and its own architecture already; this prototype lives independently so it can't regress that work, and so we're free to structure movement/animation the ALS way without fighting the existing one.

## Why this is hard, and what's already solved
- **Not hard**: getting ALS-style animations into Godot. `tools/retarget_cli.gd` + `HumanoidRetargeter` already proved this (task done in this session — walk + 3 sword-combo clips retargeted onto MotusMan, see `assets/models/als_retarget_test/`).
- **Hard part**: ALS's real complexity is in `ALSCharacter.cpp`'s AnimGraph-feeding logic — blendspace selection from speed/direction, rotation mode (Velocity Direction vs Looking Direction vs Aiming), lean/orientation warping, turn-in-place, foot IK. None of that is copyable code; it has to be re-derived in GDScript against Godot's `AnimationTree`/`AnimationNodeBlendSpace2D`, `CharacterBody3D`.
- **Source material is no longer the bottleneck**: all 126 `AnimSequence` assets under ALSV4_CPP's mannequin skeleton (locomotion 8-way walk/run/crouch, transitions/stops, turn-in-place, jump/fall/land, mantle/land-roll/get-up, lean/base poses, plus weapon-overlay/aim-offset poses) have been exported via a batched `unreal.AssetExportTask` python script (looped over all 126 paths in one `py` console call — `run_python`'s one-call-per-asset `export_fbx` op would have meant 126 separate tool calls) and copied into `assets/models/als_mannequin_standalone/full_set/`. Verified: all 126 re-imported cleanly with real Skeleton3D/AnimationPlayer/bone data (no collapsed-to-root failures). There is no dedicated "Idle" clip — ALS's idle is just holding `ALS_N_Pose` (a static base pose) plus an additive sway (`ALS_N_SecondaryMotion`), not a baked cycle; the prototype will need to approximate idle the same way (hold a pose, optionally blend in the additive) rather than looking for an idle animation that doesn't exist.
- **Animation source rule**: every animation this prototype plays must be exported from ALSHost and retargeted via the existing pipeline — never reuse this Godot project's own pre-existing clips (the pistol_starter/Mixamo pack's `W1_*`/mocap animations, or anything already under `assets/models/pistol_starter/Animation/`), even to fill an obvious gap like idle or run. If a needed clip doesn't exist yet in `als_mannequin_standalone/`, it has to be exported from ALSHost first, not borrowed. The character *mesh/skeleton* (`W1_Stand_Aim_Idle_IPC.fbx`'s embedded rig, see Phase 1) is fine to reuse — it's only the animation data that must stay ALSHost-only.

## Planned Deliverables (phased — stop and reassess after each)

1. **Scaffold**: new scene + script under `tests/manual/als_locomotion_prototype/` (or `actors/als_prototype/` if it graduates past "manual test"), a `CharacterBody3D` with a capsule collider and the **same character `player_body.gd` actually uses by default** — `res://assets/models/pistol_starter/Animation/In-Place/W1_Stand_Aim_Idle_IPC.fbx` (its embedded mesh/skeleton is what's really on screen in `foot_ik_preview.tscn`, since no `characters/*.json` catalog entry currently overrides `player_body.gd`'s `@export var character_scene` default — `MotusMan_v55.fbx` is a separate standalone file from the same pack, not what's actually rendered there). No dependency on `actors/player/*` code itself.
   - Also build varied test terrain in this scene the same way the foot IK test suite does — not by hand, reuse the existing procedural builders: `foot_ik_ramp_matrix_check.gd`'s `_build_ramp()` (CSGBox3D ramps at 15/30/45°, already parameterized by angle) and `foot_ik_stair_surfaces.gd`'s stair builder (parameterized by `step_count`/`step_height`, so a few flights at different step heights are cheap to add). Note: `foot_ik_preview.tscn` itself is flat-floor only — the ramps/stairs live in these separate dedicated check scenes, not in the preview scene.
2. **Core movement state**: grounded/falling state, walk/run/sprint speed tiers, acceleration/deceleration curves, gravity — a minimal GDScript re-implementation of `ALSCharacterMovementComponent`'s essentials, not a line-for-line port.
3. **Rotation modes**: Velocity Direction (body faces move direction) and Looking Direction (body faces camera/input forward, independent of move direction) — ALS's two baseline modes; skip Aiming mode for this phase.
4. **Animation blending**: `AnimationTree` with a 2D blendspace (forward/strafe or speed/direction) driven by the character's local-space velocity, using retargeted ALS clips. Requires exporting additional source clips from ALSHost (idle, run cycles, directional strafes) via the existing retarget CLI pipeline before this step can start for real.
5. **Jump/fall**: minimal airborne state + landing blend.
6. **Stretch, only if 1-5 feel right**: turn-in-place, reusing `player_foot_ik_modifier.gd`'s foot IK approach (don't fork a second IK implementation from scratch), basic mantling akin to `AGENT_TASKS/001_ledge_mantling_and_vaulting.md`.

## Explicit non-goals for this task
- Not touching `actors/player/*` or its foot IK stack.
- Not porting combat/melee/weapon systems — locomotion only.
- Not chasing full ALS parity (aim offsets, distance matching, ragdoll-getup) — see the open-ended discussion this task followed from.

## Open questions to resolve before/while starting
- Whether the eventual home for this is a permanent new character type in `characters/` (via `CharacterCatalog`) or stays a standalone manual test scene.

- **Phase 5 (jump/fall) done, basic version**: `ALS_N_JumpLoop`/`ALS_N_FallLoop` baked onto Y Bot (`*_on_ybot.res`). `AnimationTree` root is now a 2-state `AnimationNodeStateMachine` (`Grounded` holding the idle/walk/run 1D blendspace, `Airborne` holding a fall/jump 1D blendspace keyed by vertical-velocity sign), switched via `playback.travel()` on `is_on_floor()` edges — not an `advance_condition`, since the trigger is a one-frame edge. Verified via headless smoke tests (settle → jump → Airborne → land → Grounded transitions all confirmed).
  - **Gotcha worth remembering**: `AnimationNodeStateMachine` has no working `start_node` property in Godot 4.6 (the property doesn't exist; only `states/Start/...` sub-properties do, and an explicit `Start`→state transition with `ADVANCE_MODE_AUTO` did not change the observed initial state either). The state machine appeared to always start on `Airborne` regardless of node-add order. Fix: force it explicitly via `playback.start(...)` — but only once `AnimationTree` has processed at least one real (physics) frame; calling `.start()` synchronously in the same call that builds the tree has no effect (`parameters/playback` isn't live yet). Deferred the forced-start call to the first `_physics_process` tick instead.
